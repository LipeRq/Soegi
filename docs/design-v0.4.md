### 0-3. 先に直すべき既存の不具合（T0・新規に追加の提案）

**`AI_PROVIDER=claude` にすると、すべてのデモが動かない。**
`src/ai.js` の Claude の呼び出しは `tool_choice: {type: "tool", name}`（ツールの強制）で決まった形のJSONを返させている。設定しているモデル `claude-sonnet-5-5`（と `claude-opus-5-5`）では、**ツールの強制は 400 エラーになる**（2026-10-17、Claude API の参照で確認）。デモは DeepSeek なので今は表に出ないが、本番（お客さんのデータ）では必ず Claude を使うので、切り替えた瞬間に全部止まる。

| 項目 | 直し方 |
|---|---|
| 形の指定 | ツールをやめ、`output_config: {format: {type: "json_schema", schema}}`（構造化出力）で返させる。答えは最初の `text` ブロックの JSON |
| スキーマ | 構造化出力の制約に合わせて変換する関数を1つ作る：すべての `object` に `additionalProperties: false`、`type: ["integer","null"]` は `anyOf` に、数の上下限・文字数の制約は外す（プログラム側の検証で見る） |
| 止まった理由 | `stop_reason` が `refusal`（安全のため断った）・`max_tokens`（途中で切れた）なら、JSON として使わずエラーにする |
| 断られたとき | サーバー側の切り替え（`fallbacks: "default"`、ヘッダ `anthropic-beta: server-side-fallback-2026-07-01`）を付ける。断られたときだけ別のモデルで答え直す |
| 確かめ方 | 変換関数の単体テスト。実際の Claude での動作は、キーを入れてから台本を一度ずつ（この作業環境からは Claude にも接続できるか未確認） |
| 目安 | 1〜2時間 |

**提案：T1 の前に T0 として直す**（決めてほしいこと #1）。

### 1-2. 計算（既定値はすべて仮置き。画面で変えられる）

共通の入力：**1時間の値段**（既定 5,000円。3,000／5,000／8,000円の札＋自由入力）。

| デモ（キー） | 入力（既定値） | 浮く時間（月） | 元が取れる目安 |
|---|---|---|---|
| 経理 `receipt` | 月の枚数 100、手入力 3分/枚、導入後 1分/枚 | 枚数×(手入力−導入後)÷60 ＝ **3.3時間** | 月の金額 と 月額 |
| 労務 `attendance` | 人数 20、集計 15分/人、導入後の合計 60分 | (人数×分/人 − 導入後)÷60 ＝ **4時間** | 同上 |
| ナレッジ `knowledge` | 1日に聞かれる回数 6、1回 5分、稼働日 20、減る割合 50% | 聞かれている時間＝回数×分×日÷60 ＝ 10時間 → ×割合 ＝ **5時間** | 同上 |
| 外国人スタッフ向け `foreign` | 人数 6、説明 10分/人/日、稼働日 20、減る割合 50% | 人数×分×日÷60×割合 ＝ **10時間** | 同上 |
| 宿 `inn` | 月の通数 30、15分/通、導入後 5分/通、直接予約1組の売上 80,000円 | 通数×(分−導入後)÷60 ＝ **5時間** | 時間の比べ ＋ **年間費用÷1組の売上 ＝ 7組/年**（切り上げ） |
| チャットボット `chatbot` | 1件の成約の粗利 200,000円 | （時間の入力なし。「夜・休日の件数はお試しで測ります」と出す） | **年間費用÷粗利 ＝ 2件/年**（切り上げ） |

- 月の金額 ＝ 浮く時間 × 1時間の値段（円、1円単位で四捨五入）。表示は「月 ◯円」
- 月額・年間費用は `pricing.js` から：年間費用 ＝ 初期（無ければ0）＋ 月額×12。例：宿 15万＋3万×12 ＝ 51万円、チャットボット 10万＋2万×12 ＝ 34万円、手作業 0＋5万×12 ＝ 60万円
- どのデモがどのメニューか：経理・労務 → `manual`、ナレッジ・外国人 → `knowledge`、宿 → `inn`、チャットボット → `chatbot`
- 元が取れる時間 ＝ 月額 ÷ 1時間の値段（例：5万÷5,000円 ＝ 月10時間）。判定の文は今の `roi.js` と同じ4段階（上回る／ちょうど／あと◯時間／割に合わない可能性）
- 浮く時間が0以下（導入後のほうが長い）→ 0として計算し、「導入後の時間が今より長くなっています」を出す
- 時間は小数1桁、件数は切り上げの整数。数字は数え上げてよい（計算値なので。design-system 4-2 ④）

ナレッジの画面だけは2つ（社内の質問／外国人スタッフへの説明）を札で切り替える。

### 1-3. 浮いた時間の使い道

業種を選ぶと候補が札で出る。1つ選ぶか、自由に書く（「その他」は自由入力だけ）。

| 業種 | 候補 |
|---|---|
| 工務店・建設 | 現場の巡回／施主へのフォロー／見積の提出を早める／営業訪問 |
| 食品加工・製造 | 取引先の訪問／新商品／衛生・品質の見直し／若手の指導 |
| 宿泊 | 接客／食事の工夫／口コミ返信／直接予約を増やす取り組み |
| 税理士・会計事務所 | 顧問先との面談／経営の助言／新規顧問の獲得 |
| 介護・サービス | 利用者と向き合う時間／職員との面談／シフトの見直し |

最初に選ばれている業種：経理→税理士・会計事務所、労務→介護・サービス、ナレッジ・外国人→食品加工・製造、宿→宿泊、チャットボット→工務店・建設（相手に合わせてその場で変える）。

### 1-4. 持ち帰り1枚（A4・印刷）

- 「持ち帰り1枚を印刷する」→ `window.print()`。PDF 保存は端末の印刷機能に任せる
- 画面に見えない `<section class="takeaway">` を、いまの入力から作る。`@media print` では、これ以外を全部隠す。A4 縦、余白 12mm
- 載せるもの（上から）：日付／デモ名／業種／**「試算です。約束ではありません。お試しの1ヶ月で、御社の数字を測ります」**（必ず、先頭近くに）／入れた前提（1時間の値段を含めて全部）／浮く時間と金額（試算）／元が取れる目安／選んだ使い道／お試しで実測する項目（下表）／お試しの料金（`pricing.js`）／withsoegi.jp の QR と連絡先（080-9018-2777／info@withsoegi.jp）
- 何も保存しない（入力は画面を閉じれば消える。`localStorage` も使わない）

| デモ | お試しで実測する項目 |
|---|---|
| 経理 | 1枚あたりの入力時間／要確認になった割合／月末に入力が終わる日 |
| 労務 | 集計にかかった時間／45時間を超えそうだった人数と、月中に気づけた回数 |
| ナレッジ | 質問の件数／根拠つきで答えられた割合／「見当たりません」になった質問 |

| 宿 | 問い合わせ件数／1通の時間／返信までの時間／予約に至った件数 |
| チャットボット | 質問の件数と内容／夜・休日の件数／相談・見積依頼に進んだ件数 |

## 3. T3：FAX・紙の注文書 → 受注データ（新しいデモ `/order.html`）

### 3-1. 流れ

1 注文書を選ぶ（写真・PDF、1〜10枚）→ 2 確かめる → 3 受注データにする（経理と同じ3段階の帯）。パスワードが必要な画面。

### 3-2. 見本と架空のマスタ

| もの | 内容 |
|---|---|
| 架空の会社 | さくらんぼ食品（仮）の受注係。取引先は既存の架空の取引先（やまびこスーパー（仮）など）を使う |
| 商品マスタ `public/data/products.json` | 20品前後：コード、品名、規格、単位、入数（1ケース＝24個 など）、単価、表記ゆれ（例：「ラフランスジャム」「洋梨ジャム」） |
| 取引先マスタ | 既存の出荷ルールの3社＋2社。表記ゆれ付き |
| 注文書の見本 | **印字2枚**：取引先ごとに違うレイアウトの HTML を作り、`scripts/gen-order-samples.mjs` で JPEG にして同梱（FAX らしく灰色・ざらつき・少しの傾き）。**手書き風1枚**：手書き風の書体（Zen Kurenaido、SIL OFL 1.1）で1文字ずつ少し揺らして作る（2026-10-17 オーナー判断。#5）。画面と台本で「本物の手書きではない」と言う。中身は `public/samples/orders/samples.json`（モックの答えも同じ中身） |
| PDF | 画面で1〜3ページ目を画像にしてから送る（`pdf.js` を `public/vendor/` に同梱。`isEvalSupported: false`） |

### 3-3. AIが読む項目（`submit_order`）

発注元、発注日、納品希望日、明細（品名・規格・数量・単位・単価・金額。書いてあれば）、備考、項目ごとの確かさ（高・中・低）。読めないものは空。推測しない。

### 3-4. プログラムの確認（`public/js/order-check.js`）

| 確認 | 結果 |
|---|---|
| 商品マスタとの照合：品名＋規格が一致（全角半角・空白・中黒の違いは無視） | 一致 |
| 表記ゆれの一覧に一致、または似ている（文字の2つ組の一致率 0.6 以上） | **黄**「表記ゆれの候補：◯◯」（人が選ぶ） |
| どれにも当たらない | **黄**「未登録」 |
| 数量が空・0・数でない | **赤** |
| 単位がマスタと違う（ケースと個など） | 黄「単位を確かめてください（1ケース＝24個）」 |
| 単価がある：マスタと違う | 黄。金額がある：数量×単価 ≠ 金額 → **赤**（検算） |
| 納品日が空、過去、発注日より前 | **赤** |
| 発注元が取引先マスタに無い | 黄 |
| 同じ商品が2行 | 黄「重複の疑い」 |
| 確かさ「低」 | 黄 |

### 3-5. 出力

受注一覧（Excel・CSV）：受注No／取引先／発注日／納品日／商品コード／品名／規格／数量／単位／単価／金額／要確認。シート「取引先別」「納品日別」の集計（数式）。CSV は UTF-8（BOM付き）を既定、Shift_JIS も選べる（T4 の変換を使う）。

### 3-6. 台本で言うこと・言わないこと

「取引先ごとのレイアウトを登録しなくても読みます」。**大手の事例の数字（「1,400件以上の帳票」など）は、出典を確かめるまで画面にも台本にも書かない**。精度は見本で確かめてから言う。

完了の条件：見本3枚で、明細の品名・数量の9割以上が正しい（**本物のAIで、オーナーと確かめる**）。未登録品が黄で出る（単体テスト）。

### 3-7. 実装で決めたこと（2026-10-17）

| 決めたこと | 理由 |
|---|---|
| 候補（表記ゆれ・似ている・規格なし）は、**人が選ぶまで商品コード・マスタの単価・ケースの換算を出力に入れない**（`checkOrder` の `settled`）。取引先も、一致か人が選んだときだけコードを入れる | 候補のコードが販売管理に入ると、間違いに気づけない |
